# ADR 0051 · 项目需求聚合与角色依赖

## 决策

项目代表一个需求方部门的一次请求。每个角色仍是一条 `CapacityDemand`，由一个目标部门走现有答复、方案、预占、借调和审批流程。角色的主能力沿用需求列，最多五项额外能力存入 JSONB，每项可指定最低等级及是否必需。项目本身没有状态字段，各角色状态独立更新。

创建项目时，角色、提交事件、通知和依赖与项目同事务写入。前置角色以请求内更早角色的下标表示，因此依赖只能指向本项目且天然无环。数据库用租户复合外键隔离企业，用复合主键保证依赖边唯一。增量迁移从 `c782001bc001` 起步，并预留审批和需求事件的 `reason_code`。降级加锁后检查项目数据、依赖和已记录的原因代码，存在任一项即拒绝。

需求方项目详情复用需求方视角的需求投影。承接方从自己部门的需求进入项目时，只看到部门级角色摘要及排程。现有需求详情里的前置角色也使用同一摘要。协调方案、人员和负荷仍遵循各角色需求现有的访问权限。

## 排程

`analyze_project(roles, dependencies, outcomes)` 接收一个项目的部门级角色摘要、按需求 ID 索引的直接前置角色及最新答复结论，返回分阶段计划和影响分析，可由执行跟踪复用。计划日期优先使用承诺日期，其余取需求窗口。最早开始取直接前置角色计划结束日的次日。预计日期沿依赖传播推迟并保持各角色持续天数，项目预计完成按最晚的预计结束日计算，推迟按自然日比较原项目的最晚需求窗口。

部门仍可在角色自己的需求中协商承诺。排程只显示当前计划与依赖关系带来的影响，项目层不自动改动任何角色的承诺或人员安排。
