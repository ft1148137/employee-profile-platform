# ADR-0049：方案预占与原子承诺

状态：已采用。依据 M9 C1、E39(2)、E40、E41（D-024，2026-11-18）。

## 背景与决策

Planning 只提供建议，Capacity 才写入真实承诺。B 方代表以方案答复需求后，
必须先预占其投入，A 方接受时再按最新数据一次生成全部分配。
不带方案的旧答复继续使用接受后手工分配的流程。

新增三张租户表：`capacity_proposal`、`capacity_proposal_line`、`capacity_approval`。
提议保存来源方案 UUID，故意不加 Planning 外键；路由负责组合 Planning 的读取与 Capacity 的写入，
Capacity 不依赖 Planning。来源必须属于本需求的最新、指纹未失效快照，结论须为可行或有条件可行。
借调尚未选人不能在 C1 直接承诺。

提议状态为 pending、committed、failed、withdrawn。failed 的原因包括 rejected、expired、
recheck_failed、borrow_declined。需求最多一条 pending 提议；每个提议、审批方、提议行组合
使用 NULLS NOT DISTINCT 唯一约束。C4 借调所需的借出部门、可空员工，以及 C5 的 change 类型和
被替换提议，统一在本迁移建好，以免相邻阶段重复修改底座；本阶段不实现这些流程。

## 同人多段与容量口径

E40 要求保留每段的日期和比例。每个提议行生成一条分配，以可空的 `proposal_line_id`
和租户复合外键关联，非空行标识全局唯一于本企业。服务端另外断言分配的需求和员工与提议行归属一致。
手工输入不能指定或修改行标识；手工分配仍受原“每人每需求一条 active”约束，
已有提议分配的需求不能再手工新建分配，应进入正式变更流程。

同一员工的全部提议行按周累计，重叠段相加，与其他进行中分配、有效预占及平台外投入比较。
未确认、超过 28 天需重确认、超过可用容量均阻断承诺，没有绕过开关。
依据外人员必须显式提交 `outside_basis: true`；它只记录经理确认，不修改画像。
答复日期从行的最早开始和最晚结束派生，不信任客户端的覆盖日期。

有效预占指 pending 且 `hold_expires_at > now` 的具名提议行。固定有效期 72 小时。
`calendar.loads()` 的 platform_percent 包含预占，另返回 hold_percent，正式分配可由两者相减区分。
团队负荷的 weeks 使用同一口径。过期立即不计入负荷，不依赖任务及时运行。
Planning 的输入指纹包含其他需求的有效预占行、日期、比例、到期时间与版本；
新快照的周负荷也包含这些预占。当前需求自己的预占在重新模拟时排除，
接受时仅排除本提议自己的预占，并重新加上本提议全部段的逐周合计。
延期只排除正在修改的那条分配，同一员工其他段仍计入。

## 事务、并发和失败

所有提议、接受、拒绝、撤回、过期统一采用“需求 → 提议（若已有）→ 员工按 UUID 升序”的锁顺序。
过期只需要需求和提议锁，不取员工锁；周期任务和接受先后拿到同一提议后只能有一个终态。
既有手工分配、延期和容量记录的员工锁与此兼容，承诺复核与写入在同一事务完成。
每五分钟按企业处理过期提议，任务只负责持久化失败状态、事件和通知。

接受时重新读取双方当前身份和权限、需求版本、在职及管辖范围、能力依据及每周容量。
同一个用户不能同时充当提议人和需求方审批人，管理员、兼管双方的经理同样返回 403。
MCP 不能触发预占或方案接受；C3 负责扩展助手确认卡入口。

全部通过才写需求方审批、全部分配、accepted/committed 事件、双方及员工通知和审计。
行唯一索引与审批唯一约束兜底防重；版本或终态冲突返回 proposal_decided 和当前状态。
数据库异常或写到第二条分配时的意外异常整体回滚，提议保持 pending。
已知复核失败则必须真正落库 failed、释放预占、需求回到 submitted；
服务抛出专用 ProposalFailed，由 REST 边界先提交该状态再返回 409，其他异常不提交。
拒绝要求不超过 500 字的理由，记录需求方结论并通知重新规划；撤回也释放预占。
过期返回专用提示并保存 expired 原因。

## 隐私、审计与降级

需求方只得到部门级人数、比例集合、时间、条件、到期时间和审批角色，
只显示自己写的理由，没有人员行、姓名、员工 ID 或 B 方审批人的身份。
资源方人员姓名现查 employee_scope_clause，不在当前范围内的人员行不返回。
员工承诺生效后才从“我的分配”读取，不获得待确认提议的人员信息。
冲突提示包含周和超出比例，来源按实际接收人的需求权限过滤，不可见时仅写“其他需求”。
需求没有独立标题字段，来源显示其已有 description，不引入新标题快照。

复用既有需求及分配审计事件，details 记录提议或提议行 ID、失败原因及依据外确认。
过期审计的 actor 为 system_worker；需求事件的必填用户外键沿用提议人以记录来源，
不将其解释为新的人工审批。Evidence 和画像版本均不修改。

`downgrade()` 在同一个迁移事务内先以 `ACCESS EXCLUSIVE` 锁住 `capacity_assignment`、
`capacity_proposal`、`capacity_proposal_line`、`capacity_approval`、`capacity_demand_event`
五张表以防止检查与降级之间发生并发写入，再执行全库检查；任何解绑、`DELETE` 或破坏性 DDL
均位于检查之后。除保留原有同人同需求多条 `active` 分配阻断及其诊断外，只要存在任意
`capacity_proposal`、`capacity_proposal_line`、`capacity_approval` 记录，或任意
`capacity_assignment.proposal_line_id IS NOT NULL`（包含已结束分配），或任意
`capacity_demand_event.kind IN ('committed', 'proposal_failed')` 记录，一律报错并回滚
整个迁移事务，完整保留数据库版本（`c782001bc001`）、结构、关联与全部历史记录。仅空库或只含
兼容旧结构数据（如无 `proposal_line_id` 关联且仅含 `commitment_changed` 等旧事件）的库可降级
至 `c696001bc001` 并再次升级至 `c782001bc001`。
没有新增依赖、企业配置或通用审批引擎。
