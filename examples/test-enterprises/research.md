# 研究笔记：10 家模拟企业的设计依据

## 目的与方法

本笔记为 NERE-19 的十家完全虚构企业提供可追溯的行业与组织设计依据，而不是对任何真实企业或个人的判断。设计先以 APQC Cross-Industry PCF v8.0 的一级流程作跨行业部门映射，再以 GB/T 4754—2017 的门类和小类确定统计分类，最后把法规明确的执业、注册或安全上岗要求与企业内部职级、项目授权分开建模。[1][2][5] 除明确标注的法规事实外，部门名称、项目、岗位组合、人数、职级命名、证据记录和所有人名均是测试用合成设计；无法从可访问的权威原文核实的事项，均标为「未能核实」。

## 组织结构类型与项目权力

PMI 的公开材料把矩阵描述为项目和职能两条责任线，并指出项目经理在不同矩阵中可从协调角色到较强管理地位，项目经理与职能经理的权力可以均衡。[4] 下表将该资料用于本数据集的可测试化定义；它不是对任一真实单位结构的调查结论。

| 类型 | 本数据集定义 | 项目经理与职能经理的关系 |
| --- | --- | --- |
| 职能制 | 人员按研发、生产、质量等专业部门归属，工作资源主要由部门调配。 | 职能经理管理人员、专业发展和资源；项目负责人若存在，通常协调任务而无直接人事权。 |
| 直线职能制 | 现场或班组存在清晰的逐级指挥链，职能部门提供专业、制度或监督支持。 | 现场指挥权在直线链；职能负责人制定或监督专业要求。项目经理不是必设岗位。 |
| 事业部制 | 区域、产品或门店事业部对一组业务结果负责，职能支持可集中或下沉。 | 事业部负责人优先配置本事业部资源；跨事业部项目需协商资源。 |
| 弱矩阵 | 职能部门仍主导资源和优先级。 | 项目经理主要协调，职能经理权力较强。[4] |
| 平衡矩阵 | 项目和职能两线同时存在。 | 项目交付与专业/人员管理需要共同决策，权力大致均衡。[4] |
| 强矩阵 | 项目有较集中的预算、排期和资源控制。 | 项目经理权力相对更强，职能经理仍负责专业能力和人才供给。[4] |
| 项目制 | 交付项目是人员组织与日常工作的中心。 | 项目经理主导项目人员、范围和交付；部门负责人主要承担专业实践或业务线责任。 |
| 混合制 | 同一组织并存项目部、学院/事业部或职能部门等多种机制。 | 权力边界按项目和部门分别显式记录，避免从职位名称猜测管理关系。 |

十家合成企业的结构选择如下。这里的「为什么」是测试数据的设计理由，不是对相同行业所有组织的概括。

| 企业 | 结构 | 设计理由与权力边界 |
| --- | --- | --- |
| 青栎云（模拟） | 平衡矩阵 | 职能部门管人，采购协同、供应商门户产品线管事；产品经理担任项目经理但不是部门负责人。 |
| 栖光智联（模拟） | 职能制 | 硬件、嵌入式、算法、测试和制造工程各自管人；项目由部门负责人兼任，便于测试「部门负责人兼项目负责人」。 |
| 衡川汽车零部件（模拟） | 职能制（含车间） | 生产、质量、工艺和设备围绕稳定产线分工；车间班组的工作记录不等同于独立项目组织。 |
| 岚城银行汀州分行（模拟） | 矩阵（条线加分支） | 支行客户经理主汇报给支行，另向公司或零售金融条线接受业务指导，形成可验证的双线记录。 |
| 沐安市中心医院（模拟） | 直线职能制（科室制） | 临床科室负责诊疗组织，医务部和信息中心提供质控、制度与信息支持；MDT/科研作为跨科项目。 |
| 远衡管理咨询（模拟） | 项目制 | 项目组围绕客户交付组织，Practice 负责专业归属；Engagement Manager 可带项目而不担任部门负责人。 |
| 筑岳建设工程（模拟） | 混合制 | 项目部承担现场交付，工程、安全质量、商务和人力部门提供专业支持；另设非部门负责人的维保项目经理。 |
| 禾邻超市（模拟） | 事业部制 | 区域运营与门店形成经营单元，商品采购和人力信息提供集中支持。 |
| 岚江省电力公司（模拟） | 直线职能制 | 中心—班组保留明确指挥链，安全监察作为职能监督；工作票中的角色授权不等于部门职务。 |
| 汀兰大学（模拟） | 混合制 | 学院与行政处室并存，科研项目 PI 可跨越学院/处室线而非院长。 |

因此，青栎云的产品经理、远衡的 Engagement Manager、筑岳的小型维保项目经理和汀兰的 PI 都可被设计成「项目经理不是部门经理」。这直接覆盖 PMBOK/PMI 所述的项目与职能责任线分离情形，而不从项目头衔推断人事管理权。[4]

### 2019 年修改单与代码核验边界

任务背景提及 GB/T 4754—2017 有「2019 年第 1 号修改单」。本次检索未能从国家统计局或全国标准信息公共服务平台取得可访问的修改单原文，因此该修改单的发布、具体变更及其是否影响上表十个代码均标为「未能核实」。[6] 本文不把该未核实事项用于推断代码变更；发布或导入生产数据前，应以可取得的现行标准正文和修改单逐条复核。

### SaaS 的 6550 与 6513 取舍

解析副本中，6550「信息处理和存储支持服务」的注释包含在线软件租用和在线 ERP；6513 为「应用软件开发」。[5] 青栎云被定义为面向制造企业持续提供在线采购协同服务，而不是只交付定制软件开发成果，故测试数据选择 I 门类 6550。该选择是为了让服务运行、客户成功、SaaS 账号和 Git/Jira 证据能够同时存在，不表示所有 SaaS 企业都必须归 6550；若收入和主要活动变为受托开发，6513 是应重新评估的候选分类。[5]

### AIoT 的制造业冲突与替代方案

若栖光智联自行量产视觉模组，和衡川一样归入 C 制造业会更自然；但本数据集要求十家企业分属不同门类。因此把栖光定义为以工程研发/试验发展为主、量产委托 EMS 的企业，选择 M 门类 7320，保留 DFM、认证和供应链协同记录但不把它设为自产制造商。[5]

替代设计可以把主营活动写为物联网技术服务，归 I 门类 6532「物联网技术服务」（同属 653「信息系统集成和物联网技术服务」，另一小类是 6531「信息系统集成服务」）。[26] 但 I 门类已被青栎云（6550）占用，再用 6532 会让两家企业落在同一门类，所以没有采用。7320 的代价是栖光的统计分类偏向研发服务；如果以后不再要求门类互不相同，6532 或 C 门类的智能消费设备制造都是更直观的选择。

## 各行业岗位、职级与执业/上岗要求

以下「职级」优先区分法定职称、职业技能等级、注册/许可和企业内部命名。除医院、建造师、安全作业、教师等有明确制度的项目外，岗位序列主要是合成企业为测试画像而设，不应被读作全国统一标准。

### SaaS 软件

- 典型合成岗位为后端/前端工程师、产品经理、测试工程师、SRE/运维工程师和客户成功经理；部门流程映射依据 PCF 的产品、IT、服务和客户服务类别。[2]
- P5–P9 仅是青栎的内部职级命名，不是法定职称或统一执业资格。未为软件工程师设定通用法定「上岗证」；任何厂商云证书只作为可过期的辅助证据，不作为能力结论。

### 智能硬件 / AIoT

- 典型合成岗位为硬件工程师、嵌入式工程师、端侧算法工程师、测试/认证工程师、制造工程师和供应链工程师。
- P5–P7、M2–M3 均为内部序列。EMC、DFM、RKNN 等能力以设计评审、测试和变更记录核验；行业没有对应的个人执业许可，外部培训证书（如 EMC 培训、IPC-A-610）只作为可过期的辅助证据。

### 汽车零部件制造

- 典型合成岗位为机加工操作工、班组长、质量工程师、工艺工程师、设备维修工和供应商质量工程师；操作工可使用初级工—高级工、技师—高级技师等职业技能等级口径，管理岗 M1–M4 为内部命名。[22]
- 对焊接与热切割、电工作业等特种作业，数据应把应急管理部门《特种作业人员安全技术培训考核管理规定》下的《特种作业操作证》与具体作业类别、有效期分开记录。[11] 叉车 N1 的现行证种/主管口径本次未能核实，不将其作为本笔记的已核实法定结论。
- IATF 16949 记录企业质量体系相关要求和审核语境，不等同于个人职业许可。[7]

### 城市商业银行

- 典型合成岗位为公司客户经理、零售客户经理、柜员、运营授权员、风险合规专员和科技支持人员；「柜员 A/B/C、经理/高级经理/资深经理」只作为本行内部职级，非全国统一职称。
- 数据可保留「银行业专业人员职业资格」、证券行业专业人员水平评价测试和基金从业相关证明等字段，但它们的具体适用岗位、当前考试规则、有效性和主管/组织机构必须按证书签发信息核验。中国证券业协会、中国证券投资基金业协会和中国银行业协会的本次可访问页面未能取得完整现行规则原文，故不把「持有即可以从事某项业务」写成事实。[19][20][21]
- 反洗钱培训通过记录属于培训证据，不是以本笔记核实的统一执业许可。

### 综合医院

- 典型合成岗位为住院医师、主治医师、副主任医师、主任医师、护士、护师、主管护师、病案质控人员和信息工程师；上述医师/护理职称序列可作为医院人事字段，但具体聘任仍应以所在单位和职称制度记录为准。[8][9]
- 《中华人民共和国医师法》于 2022-03-01 施行；医师资格与医师执业注册应分开保存，且应记录执业地点/范围等注册事实，不能只凭资格证推出当前可执业范围。[8]
- 护士执业注册使用《护士执业注册管理办法》作为制度依据，记录注册状态而非只记录一次考试或学历。[9]
- 住院医师规范化培训依据国务院办公厅关于建立该制度的指导意见设计为培训经历/合格证明字段，而不是把「正在规培」当作独立执业能力。[10]

### 管理咨询

- 典型合成岗位为 Analyst、Consultant、Senior Consultant、Engagement Manager/Manager、Senior Manager 和 Partner；这是一种咨询业常见命名惯例，并非法定职称或全国统一等级。[23]
- 远衡将项目工时、交付物作者/审核人和项目复盘分开保存。合伙人、部门负责人和项目经理可重合也可分离，不能由 Partner 头衔单独推断项目管理权。

### 房屋建筑施工总承包

- 典型合成岗位为项目经理、生产经理、施工员、质量员、专职安全员、商务合约人员、劳务班组长和资料员。项目部可用项目经理/生产经理等岗位，企业职能部门可用专业序列；这些岗位名本身不自动构成执业许可。
- 一级、二级建造师应作为注册建造师资格/注册事实和专业分别记录；主管部门为住房和城乡建设主管部门，制度依据为《注册建造师管理规定》。二级建造师的跨地区注册限制可由省级住建部门公开答复佐证。[13][24]
- 建筑施工企业主要负责人、项目负责人、专职安全生产管理人员的安全生产考核合格证书通常以 A/B/C 分类记录，依据住建主管部门规章；应将证书类别、有效期、所在单位与实际岗位分开保存。[14]
- 建筑电工、架子工等如落入特种作业目录，使用应急管理部门《特种作业人员安全技术培训考核管理规定》所要求的操作证类别记录。[11]

### 连锁超市零售

- 典型合成岗位为店长、值班主管、收银员、理货员、生鲜/食品岗位、采购专员、区域督导和促销员。店长、区域经理和商品采购职级为禾邻内部命名。
- 《食品安全法》要求食品生产经营企业配备食品安全管理人员，并对从事接触直接入口食品工作的从业人员建立健康管理制度、取得健康证明后上岗；数据只记录与岗位、日期和可核验来源有关的字段，不记录健康检查细节。[15]
- 「食品安全管理员」的地方培训/证明口径可能不同。本次未核实一张可全国通用且适用于超市全体岗位的统一个人证书，故不把它写为通行执业许可。[15]

### 省级电网供电公司

- 典型合成岗位为变电检修工、输电运检工、调度员、工作票签发人、工作负责人、工作许可人和安全监察人员。初级工—高级技师可作为职业技能等级口径；班组长/中心主任是组织岗位。[22]
- 高压电工作业、低压电工作业和高处作业应按应急管理部门特种作业制度记录相应《特种作业操作证》、作业类别和有效期。[11]
- 「工作票签发人、工作负责人、工作许可人」在行业安全规程中是工作票角色/企业授权语境，不应与国家职业资格或部门经理混为一谈。可访问的标准化信息平台材料显示《电力安全工作规程》含工作票和工作许可章节；本次未能取得可全文核验的现行正式条文来确认三类角色的全部定义，因此数据只把它们作为可撤销的企业授权字段。[17]
- 关于「电工进网作业许可证」：本次未能找到《国务院关于取消一批行政许可事项的决定》（国发〔2017〕46号）中该事项的可访问原文或可信官方转载，故「2017 年已取消」标为「未能核实」。不能据此声明现行制度；数据可把一张早已过期的历史证留作误导性 HR 证据，并以特种作业操作证和企业工作票授权作为当前待核验字段。[12]

### 普通高等学校

- 典型合成岗位为助教、讲师、副教授、教授、实验师、辅导员、科研管理人员和信息化工程师；助教—教授、实验技术等是高校常见职称/岗位序列，具体评价口径由政策和学校制度共同决定。[18]
- 高等学校教师资格应作为教师资格认定事实保存，与职称、课程记录、科研项目和学生工作记录分开；依据为《教师资格条例》及教育主管部门的高校教师资格认定工作。[16][18]
- 教授兼行政职务、PI 领导科研项目或外籍教师使用英文显示名，均只是合成数据中的身份/汇报测试条件，不能从中推定教师资格或科研能力。

## 设计决策

### 对建议表的具体调整

- 为满足十家企业分别属于不同 GB/T 门类的测试约束，AIoT 企业从可能的 C 制造业改写为以研发/技术开发服务为主且量产委托 EMS 的 M 7320 企业；汽车零部件企业仍保留 C 3670。这个选择牺牲了「两家都做硬件」的表面一致性，换来分类覆盖和可测试的外包制造边界。
- 组织形态细化为职能制、直线职能制、事业部制、矩阵制、项目制和混合制，并在矩阵/项目/混合企业显式保存主汇报、第二汇报和项目经理字段。这样可测试 PMI 所述的项目与职能责任线，而不是让系统从部门名猜权力关系。[4]
- 只有青栎云、栖光智联使用 Jira；其余八家使用行业工作记录。该合成约束避免把 Jira 当作平台使用前提，并测试 CSV/业务系统证据的导入和账号映射。
- 每家保留 4–6 个部门，不是对现实组织规模的断言，而是在部门负责人、普通员工、跨部门关系和审计记录之间取得可读性与校验成本的平衡。

### 证据与真实能力的差距

`personas.yaml` 的真实能力不导入系统。每项能力有以下四种证据状态，以检验系统是否把证据强度、来源冲突和未知状态正确分开：

| 状态 | 合成设计 | 系统不应得出的结论 |
| --- | --- | --- |
| `documented` | 多来源、归属和时间线相互支持的记录。 | 不能把记录数量直接变成绩效高低。 |
| `partial` | 有任务、培训或自述，但不足以确定独立完成复杂任务。 | 不能把一次参与等同于熟练。 |
| `undocumented` | 人确实具备，系统中没有关联证据。 | 不能因没有记录断言「不会」。 |
| `misleading` | 指派人与实际贡献者不符、同名混淆、过期证书、夸大自述或评价冲突。 | 不能把单一来源或证书字段当作真实能力。 |

持证通常只反映某一资格、注册、培训或授权记录在特定时间点存在；它不能单独证明在特定场景中独立完成复杂工作的能力。法规也把资格、注册、培训和安全作业分别管理，例如医师资格与执业注册、护士注册、建造师注册和特种作业操作证并不是同一个制度。[8][9][11][13] 同理，缺少系统记录可以是新入职、离职、纸面/外部系统留档、账号未映射或根本没有被采集，因此本数据集把它建模为「未知」而非能力低下。
